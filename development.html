Access control — transcripts & private resources

Research note (2026-09-15, Grok). Goal: only people we invite (e.g. Gary) can open sensitive paths; everyone else is blocked. Public catalog + DIY /Transcripts stay open. This is planning, not yet implemented.

Why “secret” URLs alone are not enough

  • An unguessable path (long random segment) stops casual browsing and search indexing of links we never publish — useful as defense in depth.
  • It is not real access control. Anyone who gets the URL (leak, referrer log, browser history, guess from a pattern like /assets/transcripts/PSYC-100_…) can open the file with no login.
  • Rule for this site: never put PA-derived verbatim materials on a public path. If we host a private vault at all, gate it with authentication and use a non-guessable prefix.

Option A — Netlify Password / Private (site perimeter)

  • Where: Netlify dashboard → Project configuration → Visitor access / Password Protection (UI names vary by plan).
  • Password: one shared secret for production and/or Deploy Previews (Pro). Simple, no Google accounts.
  • Private / team login: only Netlify team members (and invitees) using their Netlify login — not end-user Google Identity.
  • Scope: typically the whole deploy (or previews), not “only /vault/* while Home stays public.”
  • Fit for us: good for locking the entire site before launch, or locking Deploy Previews. Poor fit for “public site + private transcript folder + Google login for Gary only.”
  • Docs: Password Protection, KB overview.

Option B — Netlify Identity + Google OAuth + path roles (recommended for a private vault)

  • What it is: app-level login for site visitors (separate from Netlify team login). Identity stayed supported after a Feb 2026 reversal of an earlier deprecation notice; new code should use @netlify/identity, not the old widget.
  • Google: enable Google under Identity → Registration → External providers, then oauthLogin('google').
  • Invite only: turn registration to Invite only so random Google users cannot self-register. Invite Gary’s Google address (and any other allowed emails) from the Netlify Identity UI.
  • Roles: set app_metadata.roles (e.g. ["vault"]) on invited users.
  • CDN gate (example _redirects):
# Allow only the vault role; everyone else → login
/private-vault-XXXXXXXX/*  /private-vault-XXXXXXXX/:splat  200!  Role=vault
/private-vault-XXXXXXXX/*  /login  401!
  • Enforced at the CDN edge with the nf_jwt cookie — not a client-side “hide the link” trick.
  • Keep /login (and Home, catalog, DIY Transcripts) outside the gated prefix.
  • Docs: Identity get started, Google / invite registration, Role-based access control.

Option C — Auth0 (or other JWT) + same role redirects

  • Netlify’s Auth0 extension (or any JWT provider that can put roles in the token) can drive the same Role=… redirect rules.
  • Use when we need MFA, richer Google Workspace controls, or enterprise SSO. Heavier than Identity for a one-person vault.
  • Do not run Netlify Identity and a third-party JWT provider on the same project at once (Netlify: pick one).

Option D — Basic auth on a path (HTTP headers)

  • Netlify custom headers can put HTTP Basic Auth on one folder. Multiple passwords possible; no Google identity, shared secrets, awkward UX on mobile.
  • Acceptable for a quick private staging folder; weaker than invite-only Google Identity for long-term transcript vaults.

Unguessable path names (use with Option B/C, never alone)

  • Host private files under something like /p/a7f3c9e2…/ or /private-vault-<random>/ — not /transcripts/ or course-code filenames that are easy to enumerate.
  • Do not link that path from public nav. Share the URL only with authorized people (or after login).
  • Still require Role=… redirects: obscurity + auth, not obscurity instead of auth.
  • Optional extras: noindex on vault pages, omit from sitemaps, keep git deploys from publishing vault binaries to a public history if we can avoid it.

Suggested plan for PubliusNakamoto

  1. Keep public: Home, Peterson Academy catalog, DIY /Transcripts how-to (no hosted PA copies).
  2. If we ever need a private demo vault: Netlify Identity, Invite only, Google provider, role vault, unguessable folder, _redirects Role gate + login fallback.
  3. Use dashboard Password / Private only if we want the whole site or previews locked before advertising — not as a substitute for per-path Google invites.
  4. Do not stack site-wide Password Protection on top of Identity unless we accept double login (perimeter session ≠ Identity session).

Not legal advice; auth choice is about access control. IP policy for PA content stays: no public redistribution of verbatim transcripts/videos.

Editing This Site with ChatGPT

This is the working routine for changes made from the laptop. It is written for both a person giving instructions and an AI carrying them out.

  1. Describe the change and request a local preview. For example: “Change the large homepage name to blue. Show me locally; do not push yet.” ChatGPT should change only the requested files and leave the live site alone.
  2. Review the local site. Open the local preview URL ChatGPT provides. The port number can vary from session to session; http://127.0.0.1:8935/ is an example only. Check the change in the browser before approving it.
  3. Give a separate push instruction. Say “push” only when the local version is approved. ChatGPT should commit the approved change, push it to the main branch of nakamotopublius/website, then verify the public site.
  4. Let Netlify publish the site. Netlify automatically deploys every successful push to main. ChatGPT should confirm that https://publiusnakamoto.com/ shows the approved change.
  5. Keep credentials private. GitHub authentication is stored in this Mac’s Keychain. Never put a personal access token in a page, commit, repository file, or chat message.

Usage note: Codex’s five-hour allowance can rise faster than the visible amount of website work, because it includes the model’s reasoning and the work of inspecting files, testing previews, using tools, and verifying deployments. For small changes, batch decisions into one local review, avoid repeated color trials, and check usage only when it is useful. Use the lightest suitable model when speed is not important.
