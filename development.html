Access control — transcripts & private resources

Research note (2026-09-15–16, Grok). Goal: only people we invite (e.g. Gary) can open sensitive paths; everyone else is blocked. Public catalog + DIY /Transcripts how-to stay open. Planning only — not implemented yet. Decision pending Gary’s review.

Decision needed soon — catalog icon → PDF

  • Desired UX: user clicks the far-right transcript icon on Peterson Academy. If authorized, open the PDF. If not, send them to a login (or “not authorized”) page instead of the file.
  • Current (development only): icons + /assets/transcripts/*.pdf are live and unguarded so we can finish content work. Do not treat this as the public posture.
  • Recommended approach: Option B below (Netlify Identity + Google, invite-only, role gate). No better lightweight Netlify-native alternative for “public catalog + private PDF folder + Google accounts we invite.”
  • Why not site-wide Password Protection alone: it locks the whole site (or previews), not “catalog public / PDFs private,” and it is a shared password, not per-person Google identity.
  • Why not client-side only: hiding the icon in JavaScript does not protect the PDF URL. The gate must be CDN _redirects Role rules (or equivalent JWT) so unauthorized requests never receive the file.

Proposed click flow (Option B)

  1. Catalog stays public; icon still points at a transcript URL under a gated prefix (today /assets/transcripts/…; preferably later an unguessable folder).
  2. Visitor without a valid Identity JWT / without role vault hits the Role rule → Netlify returns 401 and redirects to /login (page we add: “Sign in with Google” via Identity; invite-only so strangers cannot register).
  3. After Google sign-in, if that Identity user has role vault, they can open the same PDF URL (browser has nf_jwt). Optional: after login, send them back to the PDF they clicked (?redirect=…).
  4. Users we never invite never get a role → always land on login / denied, even if they guess the PDF path.

Example gate for today’s transcript folder

# Authorized (role vault) → serve file; everyone else → login
/assets/transcripts/*  /assets/transcripts/:splat  200!  Role=vault
/assets/transcripts/*  /login  401!

Prefer moving files to an unguessable prefix before advertising the site; keep the same Role pattern. DIY /Transcripts (how-to + skills) stays outside the gate.

Why “secret” URLs alone are not enough

  • An unguessable path (long random segment) stops casual browsing and search indexing of links we never publish — useful as defense in depth.
  • It is not real access control. Anyone who gets the URL (leak, referrer log, browser history, guess from a pattern like /assets/transcripts/PSYC-100_…) can open the file with no login.
  • Rule for this site: never put PA-derived verbatim materials on a public path. If we host a private vault at all, gate it with authentication and use a non-guessable prefix.

Option A — Netlify Password / Private (site perimeter)

  • Where: Netlify dashboard → Project configuration → Visitor access / Password Protection (UI names vary by plan).
  • Password: one shared secret for production and/or Deploy Previews (Pro). Simple, no Google accounts.
  • Private / team login: only Netlify team members (and invitees) using their Netlify login — not end-user Google Identity.
  • Scope: typically the whole deploy (or previews), not “only /vault/* while Home stays public.”
  • Fit for us: good for locking the entire site before launch, or locking Deploy Previews. Poor fit for “public site + private transcript folder + Google login for Gary only.”
  • Docs: Password Protection, KB overview.

Option B — Netlify Identity + Google OAuth + path roles (recommended for a private vault)

  • What it is: app-level login for site visitors (separate from Netlify team login). Identity stayed supported after a Feb 2026 reversal of an earlier deprecation notice; new code should use @netlify/identity, not the old widget.
  • Google: enable Google under Identity → Registration → External providers, then oauthLogin('google').
  • Invite only: turn registration to Invite only so random Google users cannot self-register. Invite Gary’s Google address (and any other allowed emails) from the Netlify Identity UI.
  • Roles: set app_metadata.roles (e.g. ["vault"]) on invited users.
  • CDN gate (example _redirects):
# Allow only the vault role; everyone else → login
/private-vault-XXXXXXXX/*  /private-vault-XXXXXXXX/:splat  200!  Role=vault
/private-vault-XXXXXXXX/*  /login  401!
  • Enforced at the CDN edge with the nf_jwt cookie — not a client-side “hide the link” trick.
  • Keep /login (and Home, catalog, DIY Transcripts) outside the gated prefix.
  • Docs: Identity get started, Google / invite registration, Role-based access control.

Option C — Auth0 (or other JWT) + same role redirects

  • Netlify’s Auth0 extension (or any JWT provider that can put roles in the token) can drive the same Role=… redirect rules.
  • Use when we need MFA, richer Google Workspace controls, or enterprise SSO. Heavier than Identity for a one-person vault.
  • Do not run Netlify Identity and a third-party JWT provider on the same project at once (Netlify: pick one).

Option D — Basic auth on a path (HTTP headers)

  • Netlify custom headers can put HTTP Basic Auth on one folder. Multiple passwords possible; no Google identity, shared secrets, awkward UX on mobile.
  • Acceptable for a quick private staging folder; weaker than invite-only Google Identity for long-term transcript vaults.

Unguessable path names (use with Option B/C, never alone)

  • Host private files under something like /p/a7f3c9e2…/ or /private-vault-<random>/ — not /transcripts/ or course-code filenames that are easy to enumerate.
  • Do not link that path from public nav. Share the URL only with authorized people (or after login).
  • Still require Role=… redirects: obscurity + auth, not obscurity instead of auth.
  • Optional extras: noindex on vault pages, omit from sitemaps, keep git deploys from publishing vault binaries to a public history if we can avoid it.

Practice quizzes from numbered transcripts

Reference implementation: PHIL 102 on Peterson Academy (practice-tests icon → lecture menu → overlay quiz). Reuse this prompt with another agent/session when adding quizzes for other courses.

What “done” looks like

  • Per lecture: 5 multiple-choice questions, 4 answers each.
  • Final exam: 40 questions (about five per lecture), same format.
  • Every question has a transcript cite like 2.3 (lecture 2, paragraph 3) that actually supports the correct answer.
  • Lecture quizzes: show the citation with the question. Final: show the citation only with the feedback after answering.
  • Instant feedback; running score in the header; final uses a 1 minute (1:00) per question countdown that ends the question when it expires, then advances.
  • Final exam is forward-only: no return to previous final questions; no “All lectures” / Esc / backdrop close until the exam finishes (then return to the lecture menu is allowed).
  • Brass-style correct/wrong sounds (triumphant fanfare / descending trombone wa-wa-wa) with a mute toggle (sound off by default). Scores stored in browser localStorage.
  • Catalog: practice-tests icon opens a dropdown/menu of lectures + Final Exam; each item opens the on-page quiz overlay (same pattern as video/podcast/slides). Icon order: video → podcast → slides → practice-tests.

Inputs you must have

  • A numbered course transcript (PDF or text) with paragraph ids L.P per lecture (same style as cleaned PA transcripts).
  • Official lecture titles / order for the course.
  • Course code (e.g. PHIL 102) and where catalog study-aids already live (or will live) under /assets/courses/….

After each assessment — tutor remaster report

  • When a lecture quiz or final ends, show a Tutor remaster report in the overlay.
  • List every missed / timed-out question with: prompt, student answer (or time expired), correct answer, source cite ¶ L.P, short why, and a tutor ask to re-teach that paragraph.
  • Include a citation list and a suggested paste-prompt for an AI or human tutor + the numbered transcript.
  • Provide Copy for tutor so the learner can paste into NotebookLM / Claude / a human tutor.

Copy-paste prompt

Generate practice quizzes for Peterson Academy course {COURSE_CODE} — {COURSE_TITLE} from its numbered transcript.

Reference UX (already live for PHIL 102):
- Catalog study-aid icon “practice-tests” opens a lecture menu (all lectures + Final Exam).
- Selecting an item opens an on-page overlay quiz (do not navigate away; do not force a download).
- Reuse / adapt assets from PHIL 102: quiz-player.js, quiz.css, and the catalog modal wiring on PetersonAcademy.html.

Content requirements:
1) One quiz per lecture: exactly 5 questions, 4 choices each, answer index 0–3.
2) One Final Exam: exactly 40 questions spanning all lectures (~5 per lecture), rephrased vs the lecture quizzes (same topics OK, not verbatim copies).
3) Each question MUST include:
   - prompt, choices[4], answer (0–3), cite (e.g. "3.12"), explain (short, tied to the cite).
4) cite must be a real paragraph id from the numbered transcript for that lecture. Verify every cite exists before shipping.
5) Questions should test understanding of the instructor’s points, not trivia about wording. Distractors = plausible misunderstandings.

Citation / UX rules:
- Lecture quizzes: show “Citation: ¶ {cite}” with the question; also include cite in post-answer feedback.
- Final exam: do NOT show cite on the question; reveal cite only with the answer feedback.
- Final exam: one question at a time; 60-second (1 minute) countdown per question in the header; when time expires, mark wrong / time’s up, show feedback+cite, then advance.
- Final exam: forward-only — no previous-question control; hide/disable return to the lecture menu (and Esc/backdrop dismiss) until the final completes; restore “All lectures” after finish.
- Both: running score in the header; instant feedback; mute toggle (sound OFF by default); triumphant brass fanfare on correct; descending trombone wa-wa-wa on wrong (original Web Audio — not copyrighted show clips).
- After finish: generate a Tutor remaster report of every missed/timed-out question with prompt, student vs correct answer, ¶ cite, explanation, citation list, and a suggested tutor prompt; include a Copy for tutor button.
- Persist scores in localStorage on this device; show best score when reopening.

Files to write (mirror PHIL 102 layout):
- /assets/courses/{COURSE_CODE}/quizzes/lecture-1.json … lecture-N.json
- /assets/courses/{COURSE_CODE}/quizzes/final.json
- /assets/courses/{COURSE_CODE}/quizzes/index.json
JSON shape (lecture example):
{
  "id": "{course-slug}-lecture-1",
  "course": "{COURSE_CODE}",
  "kind": "lecture",
  "lecture": 1,
  "title": "{Lecture title}",
  "questions": [
    {
      "id": "l1-q1",
      "prompt": "...",
      "choices": ["A ...", "B ...", "C ...", "D ..."],
      "answer": 0,
      "cite": "1.3",
      "explain": "..."
    }
  ]
}
Final uses "kind": "final" and no lecture number (or lecture: "Final").

Catalog wiring:
- On the course row in courses.json, set studyAidsDemo / tests menu fields:
  testLectures: [ { "lecture": 1, "title": "...", "url": "/assets/courses/{COURSE_CODE}/quizzes/lecture-1.json" }, …,
                  { "lecture": "Final", "title": "Final Exam", "url": "/assets/courses/{COURSE_CODE}/quizzes/final.json" } ]
- Ensure the practice-tests icon appears with tooltip “practice-tests” after slides in the study-aid icon order: video → podcast → slides → practice-tests.
- Wire menu clicks to the existing on-page quiz player (PaQuiz.fetchAndRender), not to a new URL page.

Process:
1) Extract/split the numbered transcript into per-lecture paragraph lists {id, text}.
2) Author all quiz JSON from those paragraphs; run a verifier that every cite id exists; fix misses.
3) Deploy via Netlify CLI (site builds from GitHub are often stopped — CLI prod deploy is authoritative).
4) Smoke-test: lecture quiz shows cite on question + sounds; final hides cite until answer, timer expires and advances, score HUD updates, mute works.

IP / posture: quizzes are original study aids derived from the student’s own numbered transcript workflow — do not republish verbatim PA transcript text inside the quiz JSON beyond short paraphrases needed for questions.

PHIL 102 files live under /assets/courses/PHIL-102/quizzes/ with shared player quiz-player.js / quiz.css. For the next course, either reuse those player files globally or copy them beside the new course’s quiz JSON.

Editing This Site with ChatGPT

This is the working routine for changes made from the laptop. It is written for both a person giving instructions and an AI carrying them out.

  1. Describe the change and request a local preview. For example: “Change the large homepage name to blue. Show me locally; do not push yet.” ChatGPT should change only the requested files and leave the live site alone.
  2. Review the local site. Open the local preview URL ChatGPT provides. The port number can vary from session to session; http://127.0.0.1:8935/ is an example only. Check the change in the browser before approving it.
  3. Give a separate push instruction. Say “push” only when the local version is approved. ChatGPT should commit the approved change, push it to the main branch of nakamotopublius/website, then verify the public site.
  4. Let Netlify publish the site. Netlify automatically deploys every successful push to main. ChatGPT should confirm that https://publiusnakamoto.com/ shows the approved change.
  5. Keep credentials private. GitHub authentication is stored in this Mac’s Keychain. Never put a personal access token in a page, commit, repository file, or chat message.

Usage note: Codex’s five-hour allowance can rise faster than the visible amount of website work, because it includes the model’s reasoning and the work of inspecting files, testing previews, using tools, and verifying deployments. For small changes, batch decisions into one local review, avoid repeated color trials, and check usage only when it is useful. Use the lightest suitable model when speed is not important.
